## Findings considered and rejected

- **"Design-system rewrite / UI redesign"**: rejected. The app has a coherent,
  tokenized design system (spacing ladder, radius ladder, Fraunces/Manrope
  type pair, semantic GST color scheme with documented WCAG-AA contrast) and
  passes the anti-ui-slop finish gate (single hero action, domain-specific
  labels, all states implemented, product-specific "Ledger" identity). A
  redesign would be churn with no evidence of user value.
- **"Optimize GstMath precision with decimal/BigInt"**: rejected. `double` is
  adequate for money values < 2^53; the real issue is *displayed rounding
  reconciliation* (plan 001), not raw precision.
- **"Add `calculate` button / debounce is enough for history"**: rejected as a
  substitute for plan 002 — the auto-save design (every result saved) is a
  stated product feature (README: "every calculation is saved locally"); the
  fix is coalescing + correct formatting, not removing the feature.
- **"Settings `resetAllSettings` (prefs.clear) is a data-loss bug"**: the
  method is dead code (no callers) — flagged as a trap in plan 008's sibling
  note instead of a standalone finding; the *used* clear-history paths already
  confirm before wiping.
- **"Support landscape orientation"**: rejected. Portrait lock in `main.dart`
  is a deliberate calculator convention; no evidence of user demand.
- **"AnimatedScale no-op in `_SlabChip`"**: rejected as a plan — one line of
  dead code, no user impact; a cleanup can ride along with plan 010.
- **"Amount field length / 15+ digit precision"**: rejected as a plan —
  unrealistic input magnitude, `FittedBox` already prevents overflow; noted in
  plan 002's maintenance notes instead.
